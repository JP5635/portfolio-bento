Article 1 / proposed teaching content

From an API Call to a Reliable AI Service

What belongs between a user request and a model provider?

Purpose. Make a model request an authenticated, observable application operation with clear failure ownership.

Mechanism to explain

Follow a request through identity, permission checks, a provider adapter, streamed output and application persistence. Distinguish application identity from provider credentials; show request IDs, response validation, rate limits, deadlines, cancellation and retry ownership. Explain the difference between receiving the final token and committing a saved result.

Original worked example and failure

Generate a maintenance summary for fictional Pump A. A fake provider finishes after the application deadline; a reconnect must distinguish an unknown result from a failed operation. Walk through a partial stream, malformed structured output and a 429 response.

Alternatives and trade-offs

Direct provider calls are simple for a controlled prototype; an application adapter owns product permissions and storage; a shared gateway can centralize provider policy but adds another operational dependency. Compare latency, ownership and portability, without claiming an adapter makes models interchangeable.

Evidence to collect

Use a fake provider to test slow replies, partial streams, 429s, malformed output and lost acknowledgements. Record time to first token, completion latency, duplicate requests and whether cancellation reached the active operation. Evaluate answer quality separately.

Article 2 / proposed teaching content

Context Is a Data Pipeline

Which information should enter this particular request?

Purpose. Provide sufficient authorized evidence while retaining the current question and staying within a model budget.

Mechanism to explain

Separate instructions, the question, historical turns, summaries, retrieved passages and tool results. Explain eligible sources → selection → deduplication → token budget → final packet. Compare character clipping with token accounting; reserve space for output. Track source identity/version and distinguish cached content from current permissions.

Original worked example and failure

The user switches from Pump A to Pump B after correcting a service date. An old summary retains the wrong pump. Build an original context manifest showing source, version, reason for selection and token estimate; compare the stored conversation with the actual packet sent.

Alternatives and trade-offs

Full-history replay preserves detail at rising cost; summaries reduce size but may retain mistakes; selected turns and on-demand reads reduce clutter but can omit a dependency. Explain compaction, persisted memory and prompt caching as different mechanisms.

Evidence to collect

Test topic switches, corrections, revoked access, long histories and conflicting versions. Check needed-evidence coverage, unauthorized inclusion, irrelevant-token share and answer support separately. Retain an inspectable packet rather than inferring input from visible chat history.

Article 3 / proposed teaching content

Beyond Embeddings: A Verifiable Retrieval Pipeline

How does a question become a reliable set of passages?

Purpose. Retrieve current, permitted evidence before asking a model to answer.

Mechanism to explain

Split ingestion from query time. Cover source IDs/versions, chunk boundaries and overlap, embedding dimensions/model compatibility, index insertion, query embedding, candidate retrieval and final context selection. Explain cosine/dot product/L2, score direction and why a score is not confidence. Introduce exact scan as a baseline and HNSW as an optional approximate index.

Original worked example and failure

An authored equipment handbook has two pressure-limit versions and a semantically similar distractor. Show a tiny vector example for intuition, then a disclosed corpus with source IDs and expected relevant passages. Replace a document and prove obsolete chunks are no longer eligible.

Alternatives and trade-offs

Exact scan is easy to inspect for a small collection; ANN indexes improve search scale with recall/latency trade-offs. Compare lexical, dense and hybrid candidates, then reranking versus a larger top-k. Compare authorization filters separately from relevance ranking.

Evidence to collect

Use held-out queries and relevance judgments: Recall@k, ranking quality where meaningful, stale-result rate, access violations and latency. Measure embedding/index time and update visibility separately. Do not let a fluent answer hide a retrieval miss.

Article 4 / proposed teaching content

Index Then Read: Retrieval Without a Vector Database

When can page structure and a two-pass reader replace embedding search?

Purpose. Navigate a small curated knowledge base while keeping evidence selection visible.

Mechanism to explain

Use a compact index of page names/descriptions. First select bounded page references; validate them against an eligible-source set; then read actual page content for the answering call. Explain content hashes for deduplication, stale indexes, structured selection output, no-match handling and an explicit fallback budget. The selector may be model-assisted; it is not automatically deterministic.

Original worked example and failure

A fictional maintenance wiki contains a current manual, an obsolete note, a troubleshooting page and a restricted report. Show the index seen by the selector and the exact pages seen by the answerer. A missing index entry causes a documented coverage failure; unsupported citations must be detected.

Alternatives and trade-offs

Explicit references are predictable when users know the source; lexical search is cheap and inspectable but can miss paraphrases; model-assisted page selection can interpret descriptions but adds latency and nondeterminism; vector retrieval suits other collection/query shapes. Avoid a universal winner.

Evidence to collect

Measure permitted-source precision/recall, index coverage, selection reproducibility, token cost and citation support. Include absent pages, malformed selector output, empty content and paraphrased questions. Inclusion and model understanding are separate observations.

Article 5 / proposed teaching content

Exact Numbers, Explained with Documents

Which part of an answer should be computed, and which part should be retrieved?

Purpose. Combine reproducible calculations with sourced policy explanations.

Mechanism to explain

Decompose a question into structured calculation and documentary interpretation. Define metric grain, joins, time windows, time zones and null handling. Use typed query inputs or validated SQL under caller permissions, then retrieve the applicable document version. Assemble a claim-to-evidence record rather than asking text retrieval to invent aggregates.

Original worked example and failure

“Which machines exceeded their service threshold last month, and why?” Use fixed-seed readings, machine records and authored service policies. Include a one-to-many join that would double-count events, a mid-month policy change and an ambiguous date boundary. Show the reference computation before drafting prose.

Alternatives and trade-offs

SQL-only answers omit policy reasoning; document-only retrieval cannot guarantee exact totals. Compare fixed orchestration with dynamic routing and preapproved query tools with generated SQL. Explain that SQL execution success alone does not establish numerical correctness.

Evidence to collect

Compare results with reference SQL and expected aggregates. Check calculation accuracy, applicable policy version, citation support, clarification behaviour and access denial separately, then run end-to-end cases. Use least-privilege fixture credentials and disposable data.

Article 6 / proposed teaching content

Running AI-Generated Analysis Within Explicit Boundaries

What constrains an action after a model proposes it?

Purpose. Permit useful computation while limiting the authority and resources available to generated code.

Mechanism to explain

Separate model planning, authorization, deterministic tool policy, human approval and execution isolation. Describe a broker that validates typed operations before launching a disposable worker. Compare namespace/process/container/VM boundaries. Cover scoped credentials, permitted files, read-only inputs, scratch outputs, egress policy, CPU/memory/time/output limits, cleanup and artifact checks.

Original worked example and failure

An original CSV includes text asking the assistant to send files to an external address. Treat it as untrusted data and trace a rejected proposal without actually contacting a destination. In an owned disposable fixture, also test a long-running task, oversized output and attempted cross-workspace file access.

Alternatives and trade-offs

SQL-only tools expose a narrow capability; general code is more flexible and needs stronger controls. Subprocesses separate execution but inherit OS authority; containers and VM-backed runtimes offer different compatibility, isolation and operational costs. Approval, tenant isolation and sandboxing are distinct.

Evidence to collect

Test broker decisions and runtime restrictions independently. Prove denied file/network access, resource termination, cancellation, cleanup and audit retention in an owned fixture. A benign task completing is not evidence that isolation works. State the residual threat model and deployment prerequisites.

Make the depth demonstrable.

Each article ships with

  • A clear purpose, input/output contract and supported scope.
  • An original fixture and one complete walkthrough.
  • A meaningful failure and recovery case.
  • An alternatives table with workload-specific trade-offs.
  • A labelled Archify diagram and source/version notes.
  • Separate correctness, cost and latency observations.

Evidence labels

  • Explained: a mechanism supported by public technical references.
  • Illustrative: original sample code not yet executed.
  • Verified locally: an executed fixture with disclosed versions and results.
  • Proposed: a design option whose controls are not yet enforced.

No throughput, quality, safety or cost claim becomes a measured result until its disclosed check has run.

Cover images

Use a restrained crop or simplified vector treatment of each article's main diagram. Keep typography, margins and a limited teal/slate palette consistent. Use generic equipment/documents as visual context. Keep the cover readable at small card size and provide a 1200 × 630 social variant. Avoid private UI screenshots or synthetic performance charts.
