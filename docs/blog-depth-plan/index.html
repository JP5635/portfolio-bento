1. Set the depth standard

Purpose → workload and contract → mechanism → architecture → worked example → failure and recovery → capabilities and limits → alternatives → verification

Every article should answer why the mechanism exists, what it guarantees, what it leaves to the application, when another tool is preferable and how a reader could test the explanation. Use a concrete, original example and public documentation. Keep client identities, private configurations, internal interfaces and production workload measurements out of the series.

The core purpose for Lakehouse Sync is recoverable publication of local analytical data into a remotely queryable table, with enough evidence to detect drift and resolve uncertain outcomes. Multipart upload is one part of that system.

2. The flagship Lakehouse Sync article

Working title

DuckDB to a queryable lakehouse: snapshots, publication and reconciliation

Target a focused 1,800–2,400-word reference article, with short explanations and links to the deeper supporting pieces. Scope it to an embedded DuckDB preparation layer and a platform-managed ingestion path. Clearly identify optional, version-dependent features.

Purpose and the responsibilities of each component

Start with an ordinary analytical use case: a local set of tabular files changes over time, and readers need a usable remote table after interruptions. Explain which source is authoritative and whether updates, deletions and external edits are in scope.

Briefly introduce DuckDB as an embedded analytical SQL engine: it scans columnar batches, can query Parquet directly, joins and aggregates locally, and can export prepared data. Projection and filter pushdown can reduce scan work when the file layout and metadata permit. This is the local preparation role; the sync coordinator supplies journalling, retries and remote reconciliation.

DuckDB architecture · Parquet access and pushdown

Explain the connection to Zetaris and object storage

Show local files → DuckDB preparation → immutable export/manifest → platform ingestion adapter → table publication/catalog → fresh Zetaris query. The lakehouse engine owns its managed data and metadata writes. Draw S3 and OCI as alternative backing stores; do not show a desktop application independently writing into a managed lakehouse table directory.

Separate two capabilities: DuckDB can access compatible object files through its filesystem extensions; a managed lakehouse table requires an appropriate ingestion or catalog interface. Placing Parquet files in a bucket does not register a table or create an Iceberg commit.

Public Zetaris documentation establishes S3/Iceberg capabilities. Treat OCI endpoint and feature support as a connector/version validation item, rather than asserting complete AWS parity. Use public interfaces and synthetic identifiers only.

Teach snapshot checks as a correctness mechanism
Snapshot or checkpointWhat it representsBoundary
DuckDB transaction viewA consistent view of data managed by that transaction.Does not freeze arbitrary external files or coordinate a remote commit.
Immutable export + manifestThe intended file set, schema and content digests for an attempt.Does not establish destination table publication.
Lakehouse table snapshotA committed table state when the table format/catalog provides it.Does not guarantee whole-file or multi-table atomicity.
Sync journalWhat the coordinator prepared, attempted and confirmed.Does not establish that another writer has left the remote table unchanged.

Outline a reconciliation algorithm: refresh remote metadata; compare with the recorded baseline; inspect relevant changes where history supports it; verify affected data; record the new confirmed baseline. Handle expired history, missing capabilities and failed observations explicitly.

A new snapshot can reflect compaction rather than changed logical rows. Equal row counts can hide edited values or a delete paired with a duplicate. Use targeted content checks or digests when correctness requires them. Define the repair ownership policy before overwriting another writer’s changes.

DuckDB transaction scope · Iceberg snapshot and commit model

Locate consistency and uncertain outcomes precisely

AWS S3 and OCI Object Storage document strong consistency. Explain delayed end-to-end visibility through ingestion, table commits, metadata refresh, caching and polling. Avoid attributing every stale query to object-storage consistency.

AWS consistency model · OCI consistency model

Track uploaded → committed → freshly query-verified as separate observations. Explain the difference between a batch being visible and the complete file being published. Atomic whole-file replacement needs a deliberate staging/version activation design.

For a lost commit reply, preserve three outcomes: confirmed committed, confirmed not committed and unknown. An unreachable verification endpoint is unknown. Reconcile before replaying work or deleting staging artifacts. State the assumptions under which the application converges: a stable source, restored connectivity, valid retries and successful reconciliation.

Finish with trade-offs, evidence and a worked example

Use two small synthetic snapshots of events and entities. Include an insert, an update and a deletion, plus a same-count modification. Walk the reader through local SQL validation, prepared partitions, a publication attempt, a lost reply, a fresh table observation and a targeted repair decision.

Explain the benefits—local analysis without a separate database service, direct columnar-file access and reproducible preparation—and the costs: coordinator state, temporary storage, schema changes, network transfer, metadata refresh and conflict ownership. Treat speed superiority as a hypothesis until measured.

7. Make every comparison testable

Correctness and recovery

Use synthetic snapshots A and B

Generate fixed-seed events and entities with documented types. Include inserts, updates, deletes, duplicates, nullable fields and schema changes. Check expected aggregates, key ownership and content digests.

Inject interruptions before/after upload acknowledgement, after remote commit but before local confirmation, during snapshot refresh and after baseline expiry. A failed observation must stay unknown.

Performance and operational fit

Measure separate workload families

Analytical: selective column scans, grouping, joins and snapshot diffs. Application: indexed point reads and concurrent small writes. Replication: offline edits and conflict handling.

Pin versions, hardware, indexes, schemas, memory/thread limits and storage layout. Report ingest/index time separately from queries; distinguish cold/warm runs and include correctness, memory, bytes read and setup cost.

The plan contains no measured performance winner. Example SQL, manifests and diagrams will be labelled as original teaching material until executed and verified. Do not compare a precomputed CouchDB view with an ad hoc join without explaining their different preparation costs.

Definition of ready to publish

  • The purpose and workload are clear in the first screen.
  • Core engine, extension, object store, coordinator, catalog and platform responsibilities are separate.
  • Support claims name the version/mode and cite a public source; unresolved provider integration is marked as a validation task.
  • The article contains a worked example, a failure/recovery explanation and a meaningful alternatives table.
  • Archify diagrams pass their validation/browser gates and are checked visually before presentation.
  • No client, private deployment, internal endpoint or private workload appears in copy, examples, diagrams or covers.
  • Performance statements follow a disclosed method and actual measurements.
